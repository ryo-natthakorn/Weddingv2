# Spec: Venue 3D Diorama (Three.js) → pivoted to Real Interactive Map

**Date:** 2026-07-24
**Status:** Pivoted — diorama (batches 1-3) shipped then REPLACED with a real Leaflet map per Ryo's feedback. Map batch 1/3 shipped.
**Type:** Feature

> **PIVOT (see Progress log):** the Three.js diorama shipped but Ryo found it decorative-only — it didn't resemble the real venue, didn't look like a map, and couldn't be used to navigate. It was replaced with a real, navigable Leaflet + OpenStreetMap/CARTO map. The sections below describe the original diorama spec; the map work is tracked in the Progress log and in the plan file.

## Problem
The Venue section currently shows a static photo card with an "Open in Google Maps" button. Ryo wants guests to be able to explore the venue, car parking, and the nearest MRT Pink Line station in a 3D view — without Google Maps Platform, which would require a billing account, an API key, and carries WebGL/coverage risk in the LINE in-app browser on iOS.

## Project constraints that apply
- Preserve the watercolor/handmade cream-peach-teal-gold-sage aesthetic ("homey," not formal).
- Primary target is iOS Safari and LINE's in-app WebKit browser — anything WebGL-based must be tested there before shipping.
- `motion` package is imported as `motion/react`, not `framer-motion`.
- Don't touch the Hero section — treat as locked.
- No new paid/billed external services (explicit request: avoid Google Cloud entirely).
- `overflow: hidden` on zero-width absolute containers is unreliable on iOS Safari — use `clipPath: "inset(0)"` instead if this pattern comes up.
- Tailwind's `bg-background` shorthand resets `background-image` — avoid it if a texture layer is needed in this component.
- IntersectionObserver refs must sit on the specific target container, not the enclosing section.
- Follow the existing planning-first process: implement in small batches, verify on Ryo's phone (Safari + LINE) between batches.

## Assumptions
- Nearest MRT: Ram Inthra Kor Mor 6 station (PK22), near Nuan Chan Intersection — confirmed by Ryo.
- Venue and parking layout will be stylized/relative (venue block, parking area, road, MRT marker), not GPS-accurate — Ryo should sanity-check relative direction/distance against a real map before this ships.
- New self-contained component (`VenueDiorama.tsx`) added alongside the existing photo card; the card and "Open in Google Maps" button stay as-is for guests who want real directions.
- Interaction: drag-to-rotate, pinch/scroll-to-zoom, camera constrained so guests can't get lost in the scene.
- Library: plain `three` (no `@react-three/fiber`) to keep the bundle smaller.
- Building geometry should resemble the real SailomSangdad silhouette (confirmed with Ryo during planning), not a generic stand-in — see Batch 2.

## Proposed change
Add a low-poly, stylized 3D diorama built with `three`, rendered in a `<canvas>` in a new component in the Venue section:
- Simplified house/venue block matching the reference photo's silhouette, in the site's palette.
- Parking area with a few simple car shapes.
- Road connecting the venue to an MRT marker labeled "Ram Inthra Kor Mor 6" (Pink Line).
- Soft/flat lighting, no photoreal textures — optionally a subtle grain/paper overlay to tie it to the rest of the site.
- No external tile service or network requests at runtime — everything is authored geometry.
- Robustness spine (added during planning, non-negotiable for the LINE/iOS target): lazy-load the three.js chunk so it never touches the initial bundle; feature-detect WebGL before mounting; wrap in a React error boundary so a runtime failure falls back silently to the existing photo card.

## Out of scope
- Hero section (locked).
- Real-world GPS accuracy / satellite imagery.
- Replacing the existing "Open in Google Maps" button.
- Gift section overlap fix, RSVP backend, spacing normalization — separate open items.
- `@react-three/fiber` / `drei` (deliberately avoided to keep the bundle small).

## PIVOT: Real interactive map (replaces the diorama)

**Why:** Ryo reviewed the shipped diorama and it failed its purpose — an invented decorative 3D scene can't resemble the real venue, can't look like Google Maps, and can't be used to navigate in the real world. Decision (confirmed): replace it with a real, navigable map. Full plan in the plan file (`.claude/plans/resume-with-existing-spec-iridescent-boot.md`).

**Coordinates:** Venue ≈ 13.84472, 100.64791 (SailomSangdad, Soi Ram Inthra 40 — **Ryo-confirmed exact pin, locked**). MRT Ram Inthra Kor Mor 6 / PK22 ≈ 13.8450, 100.6503 (Wikidata).

- **Map Batch 1 (shipped, commit 7677e0f):** removed `VenueDiorama.tsx` + `three`/`@types/three` + the now-unused `hasWebGL()`; added `leaflet`; new `VenueMap.tsx` renders real CARTO Voyager raster tiles (free, no key/billing) centered on the venue with a marker, zoom controls, and attribution. **2D `<img>` tiles, not WebGL** — more robust in LINE/iOS than the diorama. Reuses the diorama's scaffolding: lazy-loaded (chunk 567kB three → 151kB leaflet, >500kB warning gone), error-bounded, warm loading placeholder, `venueSec.inView` mount gate. `diorama_*` i18n keys repurposed to `map_*` (EN/TH). Photo card + Maps button + directions unchanged. Verified locally via headless Chromium: tiles load, real streets render with Thai labels (Ram Inthra Rd / Soi Ram Inthra 40, matching the venue address), no console errors, `npm run build` passes.
- **Map Batch 2 (shipped, commit cd117b1):** gold venue pin + pink MRT pin (inline-SVG divIcons, avoids Leaflet's broken-default-marker-image issue), bilingual popups (venue popup auto-opens, precise "Open in Google Maps" link from exact coords), `fitBounds` framing both points (fixed "too zoomed"), warm CSS filter on tiles. Verified visually via headless Chromium. **Ryo confirmed on phone: venue pin exactly right (locked); rotate/zoom felt good; one new piece of feedback: "it's not 3D."**
- **PIVOT #2 (confirmed with Ryo):** upgrade the flat map to a real tilted 3D map (real 3D buildings, like Google Maps' 3D mode) rather than keep it flat. Swap Leaflet → MapLibre GL + free OpenFreeMap vector tiles.
- **3D Batch A (shipped, commit e1feeca):** `VenueMap.tsx` rewritten on MapLibre GL (v6 — named exports only, no default export) with OpenFreeMap's `liberty` style, `pitch:55/bearing:-12`, its built-in `building-3d` fill-extrusion layer re-tinted warm; ported gold/pink pins + popups (coords flipped to `[lng,lat]`); re-added the memoized `hasWebGL()` gate (relevant again for a WebGL renderer). `npm run build` passes (chunk 963kB/253kB gz, still lazy/isolated).
  **Verification gap, logged honestly:** headless-Chromium self-verification (which worked for every prior batch) hit a wall here — WebGL context creates fine, style/sprite metadata loads, but MapLibre's Worker-based vector-tile fetch pipeline never dispatched a single `.pbf` request in that harness, so tiles/buildings never visibly render. Tested and ruled out 5 hypotheses: pitch-driven tile volume (same stall at pitch 0), Vite dev-server worker bundling (same stall against a production `vite preview` build), network/CORS (all URLs return 200 with correct CORS headers via curl), fundamental Worker incapability (a standalone Worker test responds fine in the same browser), missing software-WebGL Chromium flags (`--enable-unsafe-swiftshader` etc. made no difference). Concluded (**wrongly, see below**): Playwright/headless-Chromium-specific quirk, not an app bug.
- **Bug confirmed real, then fixed (commit a2eab17):** Ryo hit the *exact same* blank box on a real, non-headless Chrome against the deployed Vercel build — contradicting the "headless-only quirk" conclusion, so the investigation reopened. Root cause found by inspecting the actual build output: MapLibre's worker script (`maplibre-gl-worker.mjs`) itself imports a second ~470KB chunk (`maplibre-gl-shared.mjs`) via a hardcoded relative path baked in at publish time. The prior fix's `?url` import copied only the worker file verbatim — Vite/Rollup never traced *its* nested import, so `maplibre-gl-shared.mjs` was never emitted. At runtime the worker's internal import failed (silently served `index.html` via `vite preview`'s SPA fallback instead of a real 404), the worker crashed immediately after starting, and tile fetching never began — main-thread fetches (style/sprite/controls) worked fine throughout, exactly matching what both Ryo and I saw. **Fix:** copy both files byte-for-byte (unhashed, preserving their relative relationship) into `public/maplibre/`, point `setWorkerUrl()` there instead of a Vite-processed import. **Verified end-to-end this time** (not just "should work"): confirmed both files land unhashed in `dist/maplibre/` with correct byte length (not the HTML fallback), re-ran the full headless walkthrough against the production preview build — genuine tilted 3D buildings, real streets, real POI labels ("7-Eleven"), both pins, open popup, zero failed network responses; `markerCount`/`popupCount` went from 0/0 to 2/1, confirming `map.on('load')` now actually fires.
- **Style pass (shipped, commit c441415):** Ryo saw the now-rendering 3D map and gave new feedback: "it's 3d now, but the style is lacking soul - too many unrelated place - color is too google's." Root cause: OpenFreeMap's `liberty` style is tuned to look like generic web-map chrome — saturated sky-blue water, orange/yellow/white road hierarchy, bright green parks, plus every shop/restaurant/transit POI and neighborhood-name label rendering by default (that's where the earlier "real POI label" like '7-Eleven' came from — realistic, but clutter on a single-venue wayfinding map). Fix, done at the vector-tile-layer level via `map.setPaintProperty`/`setLayoutProperty` on `map.on('load')` (not a canvas CSS filter, which was tried in Batch A and only muddied the same saturated colors instead of changing them): recolored every visible base layer (water, parks/landcover, land use, the full road hierarchy + casings, buildings, road name labels) into the card's cream/gold/sage palette; hid all POI layers (`poi_r1/r7/r20/poi_transit`) and secondary place-name/water-name/route-shield layers, keeping only street names (needed for real navigability) and the venue/MRT pins. Also retinted MapLibre's own UI chrome — zoom/compass controls, popup card, attribution bar were still stark white boxes in a generic font, arguably the biggest remaining "this is Google Maps" tell — via a scoped `<style>` override; popup text now renders in TT Interphases per the site's global font rule. Verified visually via the same headless-Chromium walkthrough against a fresh production build: warm gold/tan roads and buildings, no blue water, no POI/place-name clutter, cream-tinted controls/popup/attribution, markers/popup still functioning (2/1). `npm run build` passes.
- **3D Batch B — gesture feel (shipped, commit 3111192):** Ryo gave the go-ahead to wrap up remaining polish ("scale doesn't have to be 100% match... continue to other phase" — clarified with Ryo as general permission, not a specific zoom/pitch complaint, and confirmed Music Player + Gallery are both already fully shipped from earlier sessions, so this is the last open item). Re-reading `VenueMap.tsx` found one real gap in the Batch B checklist: `scrollZoom.disable()` stopped desktop wheel-scroll from being hijacked, but nothing stopped a guest's single-finger touch-drag on mobile from panning the map instead of scrolling past it. Fixed with MapLibre's built-in `cooperativeGestures: true` — one finger now passes through to page scroll, two fingers are required to pan/rotate the map, with a bilingual hint on the wrong gesture; the hint overlay is retinted into the card's palette, and the static under-map caption updated to describe the two-finger gesture instead of contradicting it. Pitch/zoom/framing and section spacing were sanity-checked but left untouched — no concrete problem found, matching Ryo's "reasonable, not 100%" guidance. Verified via headless Chromium that the map still renders correctly with the option on; true 1-vs-2-finger gesture blocking can't be exercised in a single-point-touch headless harness, so that part is bundled into the phone check below.
